# 排查型 Agent 的能力缺口

截至 1.5.0，askJEV Agent 已具备代码测试闭环、交互终端、本地静态页面 Chrome 测试、后台会话和有预算的多轮补查。五个内置测试技能及实际验证见[能力与技能清单](testing-capabilities.md)。它仍处于限定范围的工程试用阶段；本页只列尚需补齐或扩大验证的能力。

## 按优先级补齐

| 优先级 | 能力 | 现状 | 下一步验收条件 |
| --- | --- | --- | --- |
| P0 | 用户目标与最少操作 | 最少/最多操作问答及最短成功路径仅有设计 | 从明确初始状态执行最短成功路径，再扩展省略、重复、撤回、顺序变化和边界；区分业务范围与探索预算 |
| P0 | 双轮评分与可靠性 | 当前每批一次 supported/violated/unknown 评估 | 固定同一证据和候选，独立记录两轮判断；用真实执行与保留集验证收益，高分仍须测试 |
| P0 | 现场采集 | 只读取明确列出的源码与需求 | 用户批准的日志、报错、运行参数与版本能关联到同一事故，凭据排除且不自动上传整个项目 |
| P0 | 假设与排除 | 同一模型一次生成检查项 | 保存多个原因假设、支持/反驳证据、验证动作和排除理由；信息不足时请求所需证据 |
| P0 | 多轮补查的效果 | campaign 已有时间/轮数/模型轮次预算、历史提示、失败复现和停止原因 | 在真实未知项目中证明后续轮次能增加有效覆盖；模型轮次上限不等于金额上限 |
| P0 | 缺陷复核 | 实际断言失败加模型分析；campaign 自动重现，独立断言复核仍缺失 | 独立核对断言与需求、重复复现、区分偶发失败、最小化复现、按根因去重 |
| P0 | 评分策略收益 | strict 阻塞、显式 all 故障降级和质量诊断已实现；排序效果未证明 | 在相同候选与预算下比较全测和选测的漏报、检出耗时与费用；不将诊断告警等同于校准 |
| P0 | 真实效果评估 | demo 与一个真实仓库 | 多个未参与调试的缺陷/正确/修复样本；统计误报、漏报、稳定性、时间和成本，并比较带/不带评分 |
| P1 | 项目接入 | 手工选文件与基线；16 KB 上下文 | 按报错栈与改动分析依赖、分批取证；逐步支持 API、异步、多模块及项目测试依赖 |
| P1 | 持久任务与恢复 | 1.4 已有后台会话、持久对话、状态查询与取消/重开；尚不能步骤级续跑 | 阶段检查点、查询、取消与恢复；断线后不重复有副作用的动作 |
| P1 | coding agent 协作 | 本地交接文件与回归 CLI | 可移交产物、任务接收确认、修复状态追踪与自动触发回归；自动对外提交另行授权 |
| P1 | 远端测试执行 | 本地 macOS 隔离执行 | 经验证的 Linux/ARM64 执行器；Spark 上推理可用不等于 Spark 上测试执行可用 |

## 已有证据对能力的约束

klona 首轮通用测试 10/10 通过，并未发现后来定位的 DataView 问题；边界专项才找到问题。三个失败检查项均被评分模型评为最高支持度，因而未证明评分能提升检出率。三个失败记录归属同一缺陷类型，不能计成三个独立 bug。

下一阶段的目标设计见[用户操作与评分架构](architecture/scoring-selection-v2.md)：先明确最少成功操作及最大业务范围，再扩展少见路径，评估双轮判断的实际收益，同时建立多仓库评估。现场采集、独立复核和步骤恢复仍是额外缺口。连接和 CLI 的可用性验收与排查准确率验收分别报告。

1.3 的选测与冻结重放只改变执行范围，不构成多轮自主排查。购物结算实验再次发现一个实际 bug 获得 1.0 高分，评分可靠性缺口仍存在。
