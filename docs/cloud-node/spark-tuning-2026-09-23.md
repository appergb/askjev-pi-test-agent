# DGX Spark 推理调优记录 · 2026-09-23

本轮针对 GB10 上的 `nvidia/Qwen3.8-27B-NVFP4`，分别检查持续输出速度、冷输入处理、前缀复用、并发和输出正确性。生成服务与 Open JEV 同机运行。原始证据保存在本地被忽略的 `artifacts/spark-tuning-20260923/`；[脱敏指标](../evidence/spark-tuning-2026-09-23.json)只导出允许公开的测量字段。

**当前采用 DSpark + 固定内存池，面向单路／低并发交互。** 32K 冷解码三轮中位数为 38.12 Token/s，原部署单次为 27.06；冷 prefill 未得到明显加速，8 路整组吞吐也未提高。公网入口已于本日恢复，两类密钥的流式输出、262K 上限和 Open JEV CUDA 就绪状态均已核对。

## 已确认的优化

将自动内存分配改为面向现有交互入口的固定容量：8 个运行请求、64 个 Mamba 状态槽、300,000 个 KV Token。上下文上限仍为 262,144，KV 精度仍为 FP8 E4M3，Mamba 状态仍为 float32，静态内存比例仍为 0.70。

同机测量中，生成调度进程的 GPU 内存统计从 76,707 MiB 降至 51,112 MiB，约减少 25 GiB。系统可用内存从约 15 GiB 增加到约 35.5 GiB。GB10 使用统一内存，这两组统计有重叠，不能相加。释放容量不等于单 Token 计算变快，也不代表可以同时运行 8 条满长请求。

实际容量检查很必要：保留自动分配方式时，两次重启分别只分配出 223,936 和 209,624 个 KV Token，低于接口宣称的 262,144。新验收会读取实际池容量，发现不足就拒绝计为通过。

## 测量口径

- 固定模型 revision `482ca0f3832238542f8f5295dde86b5f22711d80`，SGLang 0.5.19 / CUDA 13.0；镜像摘要见脱敏指标。
- 使用固定生成的工程资料，实际输入约 4K、32K、128K、237K；每条性能请求至少生成 1,024、最多 1,152 个 Token。
- 开启思考，temperature 0.6、top-p 0.95、top-k 20；按轮次设置相同随机种子。推测采样和执行仍可能产生不同输出及接受长度。
- 冷测前清空前缀缓存，随后立即对完全相同的提示词热测。解码速度使用服务端已接受的累计 Token，扣除整个首分片的 Token；不以 SSE 事件数或草稿提议数计数。
- TTFT 是请求发出到首个可见输出的等待时间，可能首先得到思考内容。`prompt_tokens / TTFT` 是端到端有效输入处理速度，含请求、分词和固定开销；本轮没有测 GPU 内核的纯 prefill 吞吐。
- 达到输出上限的性能样本不用于证明答案正确。JSON、工具调用、代码执行和长上下文定位另行检查。

## 原配置基线

下表各档为一次冷／热对照，不能称为多轮稳定指标。

| 实际输入 Token | 冷 TTFT | 冷解码 Token/s | 热 TTFT | 热解码 Token/s |
| ---: | ---: | ---: | ---: | ---: |
| 4,095 | 1.85 s | 30.08 | 0.28 s | 31.99 |
| 32,813 | 19.88 s | 27.06 | 0.27 s | 26.80 |
| 131,047 | 131.16 s | 22.41 | 0.50 s | 23.95 |
| 237,034 | 341.47 s | 20.31 | 0.82 s | 20.20 |

这些请求使用相同输入重放，前缀缓存显著缩短重复输入的等待时间。它不能缩短完全不同长输入的首次计算。业务侧应保持 system prompt、工具 schema 和稳定资料的序列化一致，把变化的请求内容放在后面。

## 同一内存配置下的候选筛选

以下候选均使用固定容量 `interactive`，各做一次 4K／32K 冷热对照。候选筛选不等于完整验收。

| 候选 | 4K 冷／热 Token/s | 32K 冷／热 Token/s | 32K 冷 TTFT |
| --- | ---: | ---: | ---: |
| MTP 3/1/4，8K chunk | 33.95 / 26.27 | 27.28 / 25.22 | 19.65 s |
| cuDNN FP4 | 28.58 / 26.86 | 24.92 / 30.25 | 18.68 s |
| MTP 5/1/6 | 25.75 / 33.30 | 29.54 / 27.56 | 19.77 s |
| 16K chunk | 34.31 / 33.55 | 26.56 / 24.43 | 21.02 s |

没有候选在这些样本中表现出一致的解码优势。cuDNN 的单次 32K 冷 TTFT 约减少 5%，尚不足以宣称稳定提升；16K chunk 的同项变慢。MTP 3/1/4 两个 4K 样本的平均接受长度分别为 3.72 和 2.89，说明不同输出的草稿接受情况会显著影响 Token/s，不能只选最高值。

### 独立 DSpark 草稿模型

通过已有运行时的原生 `DSparkDraftModel` 加载 `RadixArk/Qwen3.8-27B-DSpark`，固定 revision `b9a5dbdf03bc999c6c73c426b19c2d9041cea393`。只下载配置和 safetensors 权重，未执行模型仓库中的 Python 文件。权重为 3,714,723,322 字节，SHA-256 为 `2aff025f45823b40ebe726b9dfa40302f3512bd9a11c3a7347de32a567acd9a7`。

使用 7 个草稿提议、8 Token 验证宽度、FlashInfer 草稿注意力，仍保留 300,000 Token 池。首轮筛选 4K 冷／热分别为 35.83／35.26 Token/s，32K 为 38.13／37.67 Token/s。32K 冷 TTFT 为 19.54 秒，未显示冷输入处理明显加速。

DSpark 的生成进程 GPU 内存统计为 63,573 MiB，约 62.1 GiB：比精简 MTP 配置多用约 12.2 GiB，比最初配置少用约 12.8 GiB。这是草稿模型及更宽验证状态的资源取舍；不能把 MTP 配置节省的 25 GiB 直接写成 DSpark 的节省量。

### DSpark 复测

4K／32K 各执行三组冷热请求，表内取中位数；128K／237K 各执行一组。每条请求都成功生成至少 1,024 个 Token。测试期间图像任务处于空闲状态，服务没有重启。

| 实际输入 Token | 冷／热组数 | 冷 TTFT | 冷解码 Token/s | 热 TTFT | 热解码 Token/s |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4,095 | 3 | 1.85 s | 44.02 | 0.14 s | 34.80 |
| 32,813 | 3 | 19.50 s | 38.12 | 0.19 s | 41.09 |
| 131,047 | 1 | 127.46 s | 27.25 | 0.43 s | 26.23 |
| 237,034 | 1 | 326.06 s | 21.85 | 0.73 s | 23.15 |

32K 冷解码从原配置单次观测的 27.06 提升到新配置三轮中位数 38.12 Token/s，约增加 41%；128K 和 237K 的冷解码增幅分别约为 22% 和 8%。这是本次固定任务的观测，基线长输入没有三轮重复，不能写成任意任务的稳定加速比例。

三轮 4K 冷解码范围为 41.77–50.14 Token/s，热解码为 32.61–35.95；32K 冷解码为 36.66–40.45，热解码为 32.34–41.32。冷热请求可能生成不同内容，草稿接受长度随之变化，因此热请求的解码速度不必高于冷请求。

冷 prefill 的改善明显小于 decode：32K TTFT 约减少 2%，128K／237K 约减少 3%／5%，这些测量没有证明普遍的冷 prefill 加速。热缓存则将各档 TTFT 降到不足一秒，沿用的是原服务已具备的前缀缓存能力。

### 并发与长短混合

8 路请求使用相同 4K 前缀，每路输出 512 个 Token，允许共享前缀缓存。两套配置各运行一次。

| 指标 | 原部署 MTP | DSpark + 固定内存池 |
| --- | ---: | ---: |
| 整组端到端输出吞吐 | 117.15 Token/s | 109.50 Token/s |
| 逐请求解码中位数 | 19.84 Token/s | 25.05 Token/s |
| TTFT 中位数 | 7.92 s | 8.53 s |
| 最慢 TTFT | 7.93 s | 23.73 s |
| 整组完成时间 | 34.96 s | 37.41 s |

新配置提高了多数请求开始输出后的速度，但整组吞吐下降约 6.5%。日志显示其中一条请求等到先前请求完成后才进入计算，不能宣称 8 路体验全面提升。这里同时改变了草稿算法和资源上限，没有单独归因于其中一项。默认选择面向单路／低并发交互；批量吞吐需要独立优化和验收。

长短混合测试先提交 128K 冷请求，2 秒后提交同优先级的 4K 请求。新配置短请求 TTFT 为 127.11 秒，原配置为 131.20 秒；短请求解码为 31.93 Token/s，原配置为 19.96。长 prefill 对新短请求的阻塞仍然存在。

## 输出质量与服务验收

最终配置在开启思考时通过严格 JSON、工具名和参数、生成 Python 的独立容器执行，以及实际 131,065 Token 输入的前／中／后证据定位与联合回答。Open JEV 持续返回 CUDA 就绪。简单任务关闭思考后，JSON、工具调用和代码执行各重复三次，9 项全部通过；没有将未测试的通用能力计为通过。

| 简单任务 | 思考开启，单次端到端 | 思考关闭，三次中位数 |
| --- | ---: | ---: |
| JSON 提取 | 5.91 s | 1.06 s |
| 工具调用 | 3.21 s | 1.29 s |
| 代码生成及验证中的生成请求 | 65.62 s | 8.57 s |

关闭思考减少了输出量，以上是任务等待时间变化，不能当作硬件 Token/s 提升。没有更改公共服务的默认思考策略；`qwen-cloud` 的现有调用配置已选择关闭思考。

恢复入口后，从原有 HTTPS 地址核对：不带密钥返回 401，官方／用户密钥均返回正确模型及 SSE `READY`，两类响应的层级标记正确，管理接口返回 404。维护文件已删除，地址与密钥保持原样。代理同步了仓库已验证的连接取消释放槽位修复。

本地性能、质量和代理完整检查 94 项通过；随后更新恢复配置，并通过 11 项恢复路径专项检查。Python 格式、静态检查、严格类型检查及 Bash 语法检查通过。

### askJEV 真实联调

通过已安装的 askJEV Agent 1.5.0 CLI，选择 `qwen-cloud`，让 Spark 上的生成模型与 Open JEV 评分共同完成 `examples/retry-demo` 的 8 个测试。使用 `all`，没有跳过测试；完成 6 次模型交互，8 个用例全部执行，6 项通过、2 项失败。

读取交接后，两个独立根因均与示例预置缺陷一致：有效数量上限 10 被拒绝，以及同 ID／数量的重复创建没有保持幂等。使用已有 `examples/retry-demo-fixed` 复用同一批、哈希未变化的测试回归，8/8 通过，`feedback` 返回 `regression_passed`。本轮没有改写测试来获得通过，也没有修改这两份示例的业务代码。

运行 ID、测试哈希和回归摘要见脱敏指标。评分端报告了 `score_saturation` 质量诊断；全部测试仍被执行，缺陷结论来自执行断言。这次集成验证不能作为评分校准或通用缺陷发现率的证明。

## 资源竞争与恢复

基本参数筛选结束后，节点上的图像工作负载启动，新增大量统一内存占用，导致后续草稿模型试验及基线恢复遇到内存不足。这些失败启动没有计入性能对照。

经用户明确授权，等待图像任务和队列均空闲后，只释放其模型缓存，保持图像服务运行。随后恢复可用内存并重试生成服务。调优期间记录其他图像任务是否在运行，避免将资源竞争结果当成配置收益。

DSpark 复测期间的 475 次资源观测均未发现图像运行／排队任务，系统可用内存最低约 29.0 GiB。这个结果对应图像模型缓存已释放的状态；没有证明两个大模型工作负载同时达到峰值时仍有足够内存。

## 可用的后续方向

优先从实际请求入手：稳定前缀以复用缓存，减少不必要的上下文，为结构提取等简单任务显式选择是否思考。项目的 `qwen-cloud` 私密配置本来就设置了 `enable_thinking=false`；不能把这一已有设置算成本轮新增优化。

长 prefill 与短请求混合仍需单独关注。原配置中，128K 冷请求开始 2 秒后加入 4K 短请求，短请求 TTFT 达到 131.20 秒。现有优先级和分块参数没有自动消除同优先级请求的阻塞；不能仅开启一个开关就宣称问题已解决。

新内核、TensorRT-LLM 或其他引擎是独立迁移实验，需要重新验证混合 Mamba 架构、NVFP4 权重、262K 上下文、工具调用和同机评分。没有进行云节点软件升级或模型权重训练。
