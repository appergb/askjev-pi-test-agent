# DGX Spark 三值模型复现与评估 · 2026-09-25

本次目标是在 GB10 上复现作者的三值方案，保留现有 NVIDIA NVFP4 权重，并在实测后决定生产切换。用户已确认这里的“三比特”指作者的三值方案。

**候选已在 GB10 上复现并完成本轮验证，尚未切换生产。** 生产接口取舍未确定，原 SGLang 服务已恢复，候选容器停止待切换。原始证据位于本机被忽略的 `artifacts/ninfer-20260925/` 及节点对应任务目录；[脱敏证据](../evidence/ninfer-ternary-2026-09-25.json)包含测量与恢复结果。

## 作者做了什么

采用 PrismML 已发布的 `Ternary-Bonsai-2-27B`，为 NInfer 增加三值格式和 Hadamard 旋转支持，再移植 Qwen3.8 的 MTP 预测头。27B 参数规模没有变小，主要减少的是权重存储和传输量。本次未训练模型权重，也没有把现有 NVFP4 checkpoint 再次量化。

“1.58-bit”指三值符号的信息量 `log₂(3)`。本次使用的 PQ2_0 格式每 128 个权重保存 32 字节码字和 2 字节 scale，实际为 **2.125 bits/weight**。它不是 INT3。代码打包保留三值码字，完成布局、行顺序、norm 表示和旋转元数据的转换。

复现依据是作者的公开工具包、官方模型卡和源代码。CSDN 公开导读后的正文存在付费限制，没有将未取得的全文当作核查证据。

## GB10 适配与验证

编译目标为 ARM64 / `sm_121a`，使用节点已有 CUDA 13.0 和驱动；构建依赖装在独立 Docker 镜像中，没有升级宿主机软件或驱动。普通 `sm_121` 不足以编译这里的 FP8 MMA 指令，已用架构专用目标完成构建。原有低共享内存调度被保留，设备 SM 数按实测设为 48。

已完成的验证：

- 两个读取器独立核对 GGUF 的 851 个张量索引；数据起点一致。
- 全部 64 层共 402 项装配规则通过，旋转符号表 28,672 个值逐项一致。
- 作者内核的 15 个矩阵数值算例通过；优化候选经实际调用入口测试的 48 个算例通过。
- 两种旋转内核均通过六个算例及负控。发布包的 Python oracle 对多 Token 数据使用了错误的 reshape；原始失败证据与按实际 Token 布局修正后的结果分别保存。
- 同权重、同语料的 1,551 Token 困惑度对照：作者版本 `6.8279029563`，优化版本 `6.8290532800`，相对差约 `0.0168%`。这只验证本次内核改动，不能证明与原 NVFP4 模型能力等价。
- 优化候选的三次 JSON 提取、自动工具调用、生成代码的隔离执行均通过。首次代码检查对返回的 tuple/list 表示作了提示词没有要求的限制；保留原记录，并用相同模型输出核对区间值、顺序、不变性和边界条件。

## 带宽与性能口径

256 MiB CUDA 设备内复制，每轮 32 次、共五轮，并核对完整输出。读写合计有效带宽中位数为 **242.58 GB/s**，单向复制口径为 **121.29 GB/s**。这是内存复制微测试，不是模型推理的实际 DRAM 计数，也没有用 Token/s 乘权重大小冒充硬件带宽。

推理使用固定工程资料、流式 API 和服务端实际 Token 数；短档每次输出 1,152 Tokens，开启思考。早期配置的标签前缀不同；后续分块对照通过 `--prompt-tag` 固定完整提示词。达到输出上限的性能样本不算答案质量通过。当前各格为一次观测，未作统计显著性推断；推测接受率、输出内容与运行配置均会影响解码速度。

| 配置 | 4K 冷 TTFT | 4K 冷解码 | 32K 冷 TTFT | 32K 冷解码 |
| --- | ---: | ---: | ---: | ---: |
| 原生产 SGLang / NVFP4 / DSpark | 1.95 s | 58.20 Token/s | 19.46 s | 30.82 Token/s |
| 作者三值内核 / MTP 2 | 10.85 s | 51.18 Token/s | 89.85 s | 39.27 Token/s |
| 优化内核 / MTP 2 / 512 chunk | 4.37 s | 53.08 Token/s | 37.05 s | 41.89 Token/s |
| 优化内核 / MTP 2 / 2048 chunk / 600K KV 池 | 4.53 s | 58.55 Token/s | 37.62 s | 44.87 Token/s |

最后一档重复的 4K／32K 请求首 Token 约为 0.093／0.111 秒，分别命中 4,103／32,822 Tokens。扩大内存池和修改分块是同一个候选配置的两项改变，不单独归因其效果。

300K KV 池配置下，实际 131K 输入的冷请求 TTFT 为 181.45 秒、解码 35.45 Token/s；重复请求没有命中缓存，TTFT 为 182.99 秒。已保存这一失败的复用结果。该轮 237K 请求被主动中断，不计为完成。

扩大为 600,000 KV Tokens 后，长输入复用恢复。以下为优化内核、MTP 2、2048 chunk、8 并发容量、8 个额外设备状态槽、关闭主机状态／KV 缓存的完整请求结果。每格一次观测，每次均输出 1,152 Tokens：

| 实际输入 Tokens | 冷 TTFT | 冷解码 | 热 TTFT | 热解码 | 热请求缓存命中 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 131,061 | 180.77 s | 34.20 Token/s | 0.166 s | 34.19 Token/s | 131,056 |
| 237,048 | 395.52 s | 24.91 Token/s | 0.225 s | 24.91 Token/s | 237,043 |

冷 prefill 仍慢于此前 SGLang 记录，热前缀则避免了重新处理整段输入。增加缓存容量解决了本次复用失败，不能称为冷计算加速。600K 是全局 KV 池容量，单请求模型上下文上限仍为 262,144。

该配置启动报告权重 7.12 GiB、运行时分配 22.9 GiB；与旧服务相比，内存收益同时包含权重、推测后端和状态／缓存管理变化。GB10 使用统一内存，进程、CUDA 与系统内存统计不能相加。

## 上下文与接口边界

[Qwen 官方说明](https://huggingface.co/Qwen/Qwen3.8-27B#best-practices)的原生上下文是 262,144，扩展到 1,000,000 需要 YaRN 等 RoPE 缩放。该 NInfer 基座把原生上限写为 262,144，未实现对应 YaRN 路径。

已实际以 `--max-context 1000000 --kv-capacity 1000000` 尝试启动，程序退出码为 1，明确报告超过原生上下文上限。因此不能宣称本次已提供 1M。缓存池容量也不能替代模型的有效上下文验收。

该 NInfer 版本支持普通 JSON 内容、自动工具调用和 SSE，但不支持严格 JSON Schema 约束、强制／指定工具调用；严格 schema 实测返回 HTTP 400。它也没有原 SGLang 的请求优先级抢占能力。现有认证网关的密钥、入口白名单和分层并发槽可以保留，但不能因此宣称 GPU 调度功能不变。

生产切换仍需明确上述接口取舍。旧模型权重和原容器保留；恢复结果见本文最终服务状态。

## 长上下文功能与服务检查

随机证据测试实际输入 **236,975 Tokens**，模型正确返回文档前、中、后三个随机码，并将三处配额正确合计为 89。输出 312 Tokens，正常停止，端到端约 405.01 秒。这是一次长文档检索与合并回答检查，未扩展为通用长上下文准确率。

流式工具调用的函数名和参数正确；把工具结果作为下一轮消息回填后，模型按要求回答 `SCHEDULED:r9`。现有项目配置使用文本、自动工具调用和非严格工具 schema；这些常规路径与候选接口相容。

八路并发请求全部完成，运行日志实际观测到八个活跃请求。共输出 2,048 Tokens，用时约 60.00 秒，整组端到端吞吐 **34.14 Token/s**，各请求 TTFT 为 0.094–7.324 秒，允许使用已预热前缀。不能据此宣称高并发优于旧部署；旧记录使用不同输出长度，也不直接计算严格加速比。

## 已准备的切换材料

模型、二进制和镜像已按哈希固定到独立位置。节点运行目录内的 `config/ninfer-ternary.json` 保存路径、哈希和实测参数，不含密钥。公开启动脚本为 [start-ninfer-agent.sh](../../deploy/spark/start-ninfer-agent.sh)。

`bash start-ninfer-agent.sh --check` 仅核验已安装的权重、二进制和镜像；正式启动前要求旧生成容器已在维护状态下完成排空并停止。脚本只启动回环地址服务，沿用现有认证网关，不创建新公网入口、不改变密钥，也不删除旧模型。

脚本已通过 Bash 语法检查、节点上的实际哈希／镜像检查和错误哈希拒绝检查。固定镜像与已安装二进制的 `--help` 验证通过；这些检查不等于生产已切换。
