# askJEV Agent 质量与比赛演示评估

评估日期：2026-09-23。当前结论：**可以发布为可安装、可复现的工程试用版，并用于明确范围的比赛演示；尚不能宣称通用项目检测准确率或生产服务稳定性已达标。** 未提供具体赛制，本评估按功能、工程可靠性、证据完整性与现场体验判断，不提供虚构的比赛分数或排名。

源码仓库：[appergb/askjev-pi-test-agent](https://github.com/appergb/askjev-pi-test-agent)。详细脱敏结果见 [验收数据](evidence/quality-review-2026-09-23.json)。

## 前端、后端与整体

| 部分 | 已完成并验证 | 当前限制 |
| --- | --- | --- |
| 终端前端 | `askjev-cli` 安装与跨目录启动、askJEV 标识、中文流式对话、命令补全、进度和报告、取消与退出；模型固定 | 需要现有任务文件；对话只在本次进程保留；没有独立网页或桌面管理界面 |
| 本地 Agent 后端 | 批准文件快照、原基线、生成、真实 JEV 评分、选测、隔离执行、缺陷交接、原测试回归、后台会话、有限多轮任务 | 支持选定 JavaScript 模块和本地静态页面；不等于支持生产网站、任意后端 API 或整个未知仓库 |
| 模型 API 代理 | 双层认证、限速、并发名额、排队、SSE、固定模型、维护截止时间、请求体限制及取消清理 | 单进程内存队列；不是多租户计费/资源配额系统；本次修复未部署到云节点 |
| 生成与评分服务 | 默认 Flash 生成 + Spark 上 JEV 评分完成两条真实业务闭环；自托管生成有独立性能记录 | 生成服务探测曾有一次工具调用未通过；云节点正在另一个任务中调优，不能把历史数据当成当前在线保证 |

## 代码检查与修复

| 检查 | 本次结果 | 解释 |
| --- | --- | --- |
| Node 自动检查 | 51/51 通过，无跳过 | 包括终端、会话、沙箱、浏览器、选测与回归 |
| `src` 覆盖率 | 行 94.30%，分支 78.44%，函数 88.36% | 覆盖率反映代码被检查触达，不代表业务正确率；错误分支和外部环境路径仍有缺口 |
| API 代理检查 | 36/36 通过，行覆盖率 94.91% | 检查源代码和模拟网络行为，不是云端压力测试 |
| Python 静态检查 | `mypy --strict`、Ruff、Black 通过 | 作用范围为 API 代理与其测试 |
| Node 生产依赖审计 | 已知漏洞通告 0 项 | 数据库查询结果，不是完整安全审计 |
| 发布检查 | 配置/运行产物排除、安装包白名单、锁文件与入口一致性 | 私密配置与云节点地址不属于发布内容 |

新增 GitHub Actions 在 macOS 执行完整 Agent 测试与打包，在 Linux 检查 Python API 代理；不依赖私密模型凭据，不在 CI 部署云节点。代理覆盖率门槛为 90%。实际远端执行状态可查看仓库的 [Actions](https://github.com/appergb/askjev-pi-test-agent/actions)。

本次审查修复了三个可复现问题：

1. 代理在等待上游响应时被取消，会遗留并发名额，积累后使后续请求无法进入。现在异常、取消与流响应结束均归还名额。
2. 分块请求原先先读完再校验大小；现在逐块检查，超过限制立即返回 413 并停止继续读取。
3. Node 覆盖率环境自动传入隔离测试，尝试写沙箱之外的目录，让原本通过的测试被归为环境失败。现在明确禁用测试子进程的宿主覆盖率输出，同时保留既有沙箱限制。

取消和超大请求的回归用例先在修复前复现失败，修复后通过。流响应清理异常也有回归检查。

## 真实业务闭环

生成模型使用默认 `flash-direct`，评分来自真实服务，选测策略为 `all`。本次没有把新测试写入业务实现，也没有改写原测试使其通过。

| 样例 | 原版实际执行 | 检出的预置缺陷 | 本轮耗时 | 修复版原测试回归 |
| --- | --- | --- | ---: | --- |
| JavaScript TaskStore | 8 项：6 通过、2 失败 | 上限 10 被错误拒绝；相同请求重试产生重复记录 | 19.62 秒 | 8/8 通过 |
| Chrome 购物页面 | 6 项：4 通过、2 失败 | 满 100 免运费边界错误；折扣为 5% 而非 10% | 20.25 秒 | 6/6 通过 |

修复版是仓库中既有的配套样例，回归验证测试字节不变，不复用旧评分，反馈记录均为 `regression_passed`。四个问题是两个受控样例中的已知预置缺陷，不能外推到真实项目的误报率、漏报率或查错能力。真实第三方 klona 的历史验证另见 [仓库评估](mvp/github-evaluation.md)。

**本轮浏览器六个候选的支持度评分全部为 1.0，其中仍有两个真实失败。** 因此高分不能当作通过证据；默认保留全量执行。当前缺少独立断言复核、根因自动去重、混合选择与概率校准，评分对检出率的收益尚未证明。

健康检查中，评分、本地沙箱和 Chrome 通过；初次生成模型工具调用探测返回 `MODEL_TOOL_CALL_FAILED`，后续相同探测实际调用成功，两条完整业务运行也完成。保留首次失败记录，不据此声称生成服务有稳定的长期可用性。

## 云端后端性能与比赛影响

以下来自 2026-09-23 本机保存的 Spark 基线测量，**每种输入长度只有一次冷测与一次热测**。未重新对正在调优的共享节点施压，数据不代表当前候选参数的最终验收。

| 输入 | 冷首字时间 | 热首字时间 | 冷/热解码速度 |
| --- | ---: | ---: | ---: |
| 4K | 1.85 秒 | 0.28 秒 | 30.08 / 31.99 token/s |
| 32K | 19.88 秒 | 0.27 秒 | 27.06 / 26.80 token/s |
| 128K | 131.16 秒 | 0.50 秒 | 22.41 / 23.95 token/s |
| 约 237K | 341.47 秒 | 0.82 秒 | 20.31 / 20.20 token/s |

八路 4K 请求的单次总输出吞吐为 117.15 token/s，首字时间中位数 7.92 秒。混合 128K 长请求与 4K 短请求时，短请求首字约 131.20 秒。这说明长预填充会明显阻塞交互，需要继续验证调度与资源隔离。

这些性能请求均可能达到输出长度上限；八并发样本没有产出最终回答文本，不能把吞吐数字当成答案质量通过。另一次 JSON schema、工具调用、可执行代码与 JEV CUDA 就绪检查各通过一项，但没有完成长上下文联合推理质量的完整重复验收。

当前工作目录中的启动参数、DSpark 候选和基准工具仍由另一个任务持续修改，本次发布保留原稳定启动基线，不将这些实验草稿合入。本评估没有重启、部署或修改云节点服务。

## 适合如何参赛

演示主线可以使用短小、已授权的样例，展示“输入需求 → 真实测试 → 失败证据 → 修复 → 原测试通过”。终端已可用，执行与证据链比单纯输出一段模型结论更完整。若比赛允许外部生成 API，应明确说明默认生成来自 Flash，Spark 承担 JEV 评分；不能把外部生成也计入本机 GPU 的贡献。

若赛制考察未知项目检错、评分节省成本、高并发服务或长上下文交互，当前证据还不够。优先补齐：多仓库盲测与误报/漏报统计、评分与不评分的时间/成本对照、长短请求混跑的重复测量、独立断言复核，以及 Linux 执行器。现场不要依赖超长冷输入或尚在试验的模型参数。

源码公开不等于功能、准确率或云端服务都已完成最终验收。当前定位仍是工程试用版。
