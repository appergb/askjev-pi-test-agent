# Pi 测试智能体 MVP 1.0 评估

日期：2026-09-21。

这是 1.0 历史验收记录；当前状态见 [1.1 真实项目评估](github-evaluation.md)。原始产物不上传 GitHub，本机索引为 `docs/mvp/evidence.local.md`。

## 结论

本地 Pi → askJEV → 现有云端 Open JEV → Pi 编写并执行测试 → 缺陷报告 → Codex 修复 → 原测试回归的闭环已跑通。默认采用 Flash 直连，GLM 5.3 作为已验证的备选。现有评分后端能够返回合法结果，但它的排序效果不稳定，不能据高分跳过测试。

这是限定于 macOS、无依赖 Node.js ESM 小项目的 MVP 验收，不是原始 v0.1 全部产品要求的完成声明。

云端千问最终版本也完成完整链路，原测试在修复版回归 8/8 通过，报告阶段已不再因摘录格式卡住：真实报告（本机原始产物）。本轮同样发现两个预置缺陷，但完成速度仍明显慢于 Flash 与 GLM，因此保留为可选模型。

## 评分效果

固定 supported / violated / unknown 候选，5 个受控场景各测 3 次，共 15 次，12 次符合预期。求和正确、求和错误、边界正确、源码缺失四个场景均判断正确；边界错误场景连续三次被判为 supported。此处 12/15 仅是这组小样例的结果，不能外推为总体准确率。

真实 demo 的首轮 GLM 检查项中，两个真正失败项的 supported 分数均为 1；调整生成模型和检查项表述后的 Flash 运行中，相同两类缺陷又得到低分，其他通过项也出现低分。这说明结果对输入措辞敏感，跨检查项比较尚不可靠。保留全部已准备测试，是本轮没有因高分漏测的关键。

原始结果：评分对照（本机原始产物）、模型小任务比较（本机原始产物）。

## 已验证的交付能力

- 固定 Pi 0.85.1 的专用 SDK 运行时；只加载本项目 Skills 和工具。
- 四个 Pi Skills 与一个 Codex 检测 Skill，全部通过结构校验。
- askJEV 真实接口适配、逐项关联、缺失/无效/未知评分处理和有限重试。
- 当前工作区内容快照、独立执行副本和业务源文件一致性检查。
- Pi 自主生成 node:test 测试，实际执行并区分断言、测试程序和环境失败。
- 19 项基础设施检查通过，覆盖 Mock 标记、真实 Pi SDK 工具工作流、路径限制、文件保护、网络禁止、子进程禁止、超时、取消、回归和证据真实性。
- 运行中显式取消返回 cancelled、退出码 5；10 秒总预算测试返回 partial、退出码 4，未假装完成。
- 修复后执行字节不变的原测试，使用新快照，不复用旧评分。
- 依赖检查报告 0 个已知漏洞；项目交付文件通过本机凭据和云节点身份扫描。

网络限制使用可访问的本机服务做正负对照：宿主控制请求成功，沙箱请求未到达服务。文件与符号链接限制也通过实际读写尝试验证。

## 本轮迭代和未通过项

云端千问首轮错误地把 assert.doesNotThrow 的返回值当作业务函数返回值，导致生成测试错误，并在预算耗尽后返回部分结果。该错误没有被计为确认产品缺陷。已把正确用法补入 writing-tests Skill。

逐字复制多行执行日志导致千问反复触发报告校验失败。最终实现改为由执行器按 case_id 附上真实日志；Pi 提供原因和影响分析。模型给出的可选摘录只有在实际日志中存在时才保留，否则替换为执行器摘录，避免虚构证据和无意义的格式重试。

原型阶段统计字段 test_assertions 实际记录的是 node:test 测试块数量；最终实现已更名为 executed_tests。历史原始产物保留原样，不将其数字解读为断言数量。

尚未实现 MCP、其他测试框架、跨平台隔离、任意仓库的既有基线自动识别和完整生产权限管理。模型间对比是少量串行/低并发任务观测，不是性能 SLA 或总体检出率实验。

## 后续增强优先级

1. 建立更大的真实代码与明确预期评估集，先解决评分的提示敏感性和漏判，再决定是否缩减测试预算。
2. 在相同候选集合和总预算下比较有/无评分的去重缺陷、首次发现耗时和误报。
3. 扩展首个真实业务项目的测试框架、既有基线与执行配置，再按需要增加 MCP 入口。
