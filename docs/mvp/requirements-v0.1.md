# 基于 Pi 二次开发的测试专用智能体
## 需求规格说明书 v0.1

**核心自研工具：`askJEV`**  
**文档日期：2026-09-21**  
**文档状态：开发评审稿**  
**使用对象：产品负责人、Pi／工具开发、模型服务开发、Codex 集成开发、测试团队**

> 项目定义：在团队已进行二次开发的 Pi 基础上，集成自研 `askJEV` 工具和测试 Skills，形成能够整理项目上下文、请求 Jive 评分、定向编写并执行测试、输出缺陷证据的测试专用智能体；通过自研 CLI 或 MCP 接入 Codex，也支持直接向用户交付结果。

本文以本轮确认的需求为依据，不代表已经审查或验证现有代码。标注“已确认”的内容是产品边界；接口字段、命令占位符和验收细则属于本稿提出的开发规格；标注“待确认”的内容不得被当成已经选定的技术方案。

## 1. 项目目标与已确认要求

### 1.1 项目具体解决什么问题

业务开发仍由 Codex 承担。进入测试阶段后，将检测任务交给我们基于 Pi 二次开发的测试智能体，由 Pi 的生成式模型理解需求、整理代码与上下文，使用 `askJEV` 连接团队的 Jive 评分后端，再根据返回结果选择测试重点、自主编写与执行测试，输出可以复现和继续处理的问题。

产品需要同时满足两种交付要求：一是将可复用的能力提炼到 Skills 中；二是将运行时、Skills、自研工具和配置整体打包，交付一套可独立调用的测试智能体，而不只是几份提示词。

### 1.2 已确认的产品边界

| 编号 | 已确认要求 |
| --- | --- |

### 1.3 首版范围与非目标

首版范围为：改造后的 Pi 运行时、自研 `askJEV` 对接、Pi 测试 Skills、任务与结果协议、受控测试执行、报告输出，以及至少一种可用的外部接入方式。CLI 和 MCP 哪个先交付尚未确认；本文分别定义两者的要求，不要求首版无条件同时实现。

本轮不默认包含评分模型从零训练、不另建多智能体调度平台、不开发图形界面或 SaaS 管理平台、不让 Pi 接管业务修复、不承诺一次检测覆盖所有语言与框架，也不预设具体模型、量化方案或吞吐指标。`askJEV` 自研不等于底层模型必须自研训练。

## 2. 名称、角色与职责

| 组件 | 定义与职责 | 明确不承担 |
| --- | --- | --- |
| Codex | 外部业务开发智能体，发起检测、消费结果、修复业务代码。 | 本项目流程中的测试编写。 |
| Codex 检测 Skill | 指导 Codex 提交任务、调用 CLI／MCP、等待结果、理解报告与发起回归。 | 在 Codex 内复制 Pi 的测试流程。 |
| 自研 CLI | 对外命令行入口，包装并调用改造后的 Pi，管理请求、进度和返回值。 | 自行做模型评分或代码分析。 |
| MCP 适配器 | 对外暴露测试能力，复用与 CLI 相同的测试内核及数据协议。 | 第二套独立测试引擎，或主动“推送进任意 Codex 会话”。 |
| Pi 测试智能体 | 基于 Pi 二次开发的运行时，以及其调用的生成式模型；组织上下文、评分调用、测试与报告。 | 业务实现修复；Pi 本身也不是评分模型名称。 |
| Pi 测试 Skills | 描述场景构思、`askJEV` 使用、测试编写和缺陷分析的流程。 | 用说明文字替代工具实现或权限控制。 |
| `askJEV` 工具 | 团队自研的 Jive 连接与结果处理工具，承担协议、认证、校验、超时和错误映射。 | 接管 Pi 的语义整理、编写测试或修改业务代码。 |
| Jive 后端 | 团队指定的评分／判断服务；本稿以最新口述中的 Jive 指代它。 | 默认视为现成外部产品，或推定其模型训练方式。 |
| 测试执行层 | 在受控环境执行 Pi 生成或选定的测试，收集实际结果与证据。 | 以模型回答冒充真实测试执行。 |

**Skill 命名约定：** `askJEV` 始终是工具与能力的展示名称。为兼容 Skill 元数据命名规则，建议 Pi 侧 Skill 的机器标识使用 `ask-jev`，正文明确调用工具 `askJEV`。这是技术标识映射，不是给工具改名。Pi 的官方 Skill 文档规定元数据名称使用小写字母、数字和连字符。[T1]

## 3. 总体架构

```text
调用方：用户，或 Codex（经自研「检测 Skill」）
               ↓
外部入口：自研 CLI 或 MCP
               ↓
统一任务协议／结果协议
               ↓
团队二次开发后的 Pi 测试内核
  ├─ 测试专用提示词与流程控制
  ├─ 生成式模型：整理、规划、编写、分析
  ├─ Pi Skills：
  │  ask-jev / brainstorming / writing-tests / bugs
  ├─ 自研 askJEV 工具 ⇄ Jive 后端
  └─ 测试执行层 → 隔离测试环境
               ↓
测试结果、日志、缺陷证据
               ↓
结构化结果 + 可读报告
               ↓
返回用户，或由入口返回 Codex
               ↓
Codex 修复 → 再次调用 Pi 回归
```

CLI 与 MCP 只是调用入口的差异，应复用同一测试内核。Pi 与 Jive 分别承担生成／编排和评分职责。`askJEV` 是 Pi 到 Jive 的工具边界，不是 Pi 到 Codex 的入口。

Pi 官方 SDK 提供会话创建、资源加载和事件订阅等嵌入能力，可以作为封装参考；实际实现必须以团队现有 fork／改造代码及锁定版本为准，不强制切换上游最新版本。[T2]

## 4. 端到端业务流程

| 阶段 | 责任方 | 输入与处理 | 输出 |
| --- | --- | --- | --- |
| 1. 提交任务 | 用户或 Codex | 提供项目、检测目标、范围、需求依据与预算。Codex 经检测 Skill 调用入口。 | TestTask。 |
| 2. 准备环境 | CLI／MCP 与 Pi | 校验配置、权限和测试环境；固定被测快照；识别已有测试并在授权范围内建立基线。 | run_id、snapshot_id、基线结果。 |
| 3. 整理内容 | Pi | 阅读需求与源码，收集必要依赖，生成场景和具体检查项，标记未知信息。 | InspectionItem 与 PreparedContext。 |
| 4. 请求评分 | Pi → askJEV → Jive | Pi 提交整理好的内容；工具校验并发送；Jive 返回评分／判断。 | 带检查项标识、评分语义与状态的结果。 |
| 5. 制定测试 | Pi | 在明确评分方向后选取重点；保留必要基础测试；在预算内安排补充测试。 | 有依据的测试计划。 |
| 6. 编写并执行 | Pi 与执行层 | 生成测试文件、数据和断言，调用真实测试框架，收集日志和断言结果。 | 测试产物与 TestExecution。 |
| 7. 分析与交付 | Pi 与入口 | 区分产品问题、测试错误、环境失败和不稳定结果，整理复现证据。 | RunResult、报告、测试文件／补丁。 |
| 8. 修复回归 | Codex → Pi | Codex 修复业务代码；新快照上重跑复现用例和相关回归。 | 回归结果，关联原 run_id／finding_id。 |

允许在预算内进行“补充上下文 → 再评分”或“补充测试 → 再分析”的循环。任务必须受执行时间、模型调用、测试数量和迭代次数约束，不得无限循环。

## 5. 功能需求

### F-01 任务接入与快照

必须接收自然语言检测目标和结构化项目范围；支持调用方指定相关文件、已有测试入口以及需求引用。首版不要求自动识别所有技术栈，但必须声明支持的框架与版本。

每次执行分配唯一 `run_id`，固定被测代码快照并生成 `snapshot_id`。快照应包含范围内被纳入测试的已提交代码、未提交修改和必要未跟踪文件，遵守排除规则；不能只记 Git commit 后忽略工作区变化。无 Git 的项目也应使用文件清单与内容摘要标识版本。

任务默认在独立工作副本／工作区运行，不覆盖用户未提交修改。同一原项目的并发任务必须通过隔离工作区或互斥策略避免互相污染。新代码快照不可无条件复用旧评分。

### F-02 Pi 二次开发与运行时

在团队现有改造基础上完善：测试专用启动配置、任务注入、Skill 加载、自研工具注册、模型配置、非交互执行、状态采集、取消与结果导出。非交互任务遇到必须授权但没有授权的信息时，返回明确的阻塞状态，不等待不可见的交互输入。

必须锁定 Pi 上游基线、团队补丁／fork 版本、模型配置和 Skill 版本，并写入运行清单。支持测试 Skills 与工具以独立模块维护，但不要求新增多个 Agent。

运行时应只加载项目批准的 Skills、扩展和工具；不得因用户电脑已有全局 Pi 配置而静默改变测试模型、工具权限或流程。Pi 官方扩展机制支持注册自定义工具，可用于 `askJEV` 的接入参考；本项目的权限限制仍须由实际执行边界落实。[T3]

### F-03 两侧 Skills

| 所在侧 | Skill | 必需内容与边界 |
| --- | --- | --- |
| Codex | 检测 Skill，最终名称待定 | 触发场景、CLI／MCP 调用、参数、等待／取消、结果解读、修复后复测。不得转而自行编写测试来替代 Pi。 |
| Pi | `ask-jev`，展示为 askJEV | 输入准备标准、调用时机、评分含义、异常处理、如何将结果用于测试。工具凭据不能写入 Skill。 |
| Pi | `brainstorming` | 从需求和源码生成边界、异常与长尾场景，标注依据与假设。 |
| Pi | `writing-tests` | 生成可执行测试、断言和测试数据；运行、分析执行结果及回归。 |
| Pi | `bugs` | 归因、去重、复现与证据整理，不凭评分确认缺陷。 |

`askJEV` 对应 Skill 和完整测试闭环为首版必须。其余三个能力需要具备，但是否在首版拆为三个独立 Skill 可以随开发拆分确认，不强制从多个文件数量衡量能力完成度。

每个交付 Skill 必须包含触发条件、输入输出、步骤、工具依赖、失败处理、权限边界和至少一个示例。Codex 官方文档支持以 `SKILL.md` 配合脚本和参考资料组织检测 Skill；安装路径与调用方式随目标版本验证。[T4]

### F-04 Pi 的内容整理

Pi 必须负责：识别检测目标、阅读相关代码、提取需求约束、形成检查项、选择必要上下文、控制内容长度和补全信息。文件读取辅助工具可以搬运源码，但语义整理责任仍属于 Pi。

每个检查项至少描述“检查哪里、在什么前提和场景下、期望什么行为、依据是什么”。预期依据优先来自明确需求、接口契约、业务不变量或已批准的行为说明。已有测试可以作为参考，但与需求冲突时应标注冲突；不能仅凭当前实现反推出预期，再据此证明实现正确。

提交给 Jive 的材料应包含必要源码原文和来源标识，不得只有模型摘要。只收集与目标有关的内容，不默认把整个仓库发送给后端。信息不足时保留未知状态，由 Pi 补充；无法补充的检查项标记为受阻或仅探索性验证。

### F-05 自研 askJEV 工具

工具接收 Pi 已整理的上下文与检查项，完成请求序列化、后端认证、传输、返回校验、错误映射和必要的确定性格式转换。允许检查文件引用、摘要和字段完整性，不另行调用生成式模型重做业务内容整理。

请求与结果必须保持 `run_id`、`snapshot_id`、`case_id` 的关联。支持单项或批量提交，取决于 Jive 真实协议；适配层不得把批量接口假定为后端既有能力。部分检查项返回失败时，应保留已成功的结果。

工具必须区分正常评分、需要补充信息、未评分、无效输出和传输错误。超时、鉴权失败、空结果、非法数值、重复／未知 ID 不能转换成低分或零分。仅对可重试错误做有上限的重试；纯评分请求重试使用稳定请求标识，不重复执行测试。

提供可控 Mock 后端用于联调，并明确标记 `backend_mode=mock`；真实后端验收不能由 Mock 代替。运行记录保留工具版本、后端／模型标识、评分配置版本、请求耗时和脱敏后的错误。

### F-06 评分语义与测试优先级

用户要求保留低分优先的测试思路。本稿建议以“实现满足指定预期行为的支持度”作为首个评分目标；它是拟定接口语义，不代表 Jive 已经返回该含义。

| 分数含义 | 对应优先级方向 | 约束 |
| --- | --- | --- |
| 满足预期行为的支持度 | 较低分优先加测 | 与本稿建议的首版策略一致。 |
| 存在指定缺陷的支持度 | 较高分优先加测 | 不得沿用低分优先。 |
| 场景发生率／稀有度 | 按长尾策略另行选择 | 少见不等于更容易失败；无运行数据时不能称真实用户概率。 |

后端必须声明分数类型、取值范围、事件／命题、排序方向与可比较范围。候选选择分布不能直接当作每项独立正确性概率；若后端输出的是选择分布，需要明确候选集合及适用方式，否则不进入低分排序。

评分语义未声明时，禁止猜测方向；按配置终止评分链路，或明确降级为非评分测试。分数默认作为原始排序信号，不宣称真实故障率或经过项目校准。不同模型、不同问题模板或不同检查类型的分数，只有明确规定可比较时才合并排序。

基础回归与明确必测的要求不能因模型高分被跳过。额外测试预算可覆盖低分项、未覆盖／长尾项和其他探索项；比例与阈值配置化，本稿不写死未经确认的数值。

### F-07 测试生成与真实执行

Pi 按项目声明的框架生成测试文件、输入数据、前置条件和断言，保存 `case_id` 到测试的映射。支持针对被测模块编写单元或集成测试；故障注入只在专门批准的隔离环境内启用。

执行层必须捕获真实命令、工作目录、退出状态、stdout／stderr、断言信息、开始结束时间及必要产物。命令以结构化参数传递，避免把模型文字直接拼接为不受控 shell 指令。覆盖率只在框架提供时记录，不伪造覆盖数字。

新生成测试出现语法／运行错误时，Pi 可以在预算内修正测试与辅助文件；不允许修改业务实现、放宽需求或删改有效断言来制造通过结果。业务源码与关键配置应按允许规则校验未被擅自改动。

### F-08 缺陷分析与结果输出

结果至少区分：已确认产品缺陷、疑似问题、生成测试错误、环境错误、既有基线失败、不稳定结果和本轮未观察到失败。既有基线失败可以形成报告，但不能计为本轮新发现。

已确认缺陷至少需要明确预期依据、对应快照、实际失败证据和可执行复现步骤；不能仅凭模型判断确认。间歇性问题应保留运行次数与复现比例，标记限制；本轮测试通过也不能表述为“代码已证明无 bug”。

每次任务应输出结构化结果、可读报告、测试文件／补丁和必要证据引用。报告必须包括检测范围、执行统计、问题与严重性依据、未执行部分、降级情况和复现命令。严重性由实际影响判断，不直接用评分大小替代。

面向 Codex 的结果应能支持后续定位与修复，不要求它重新阅读整个 Pi 会话。记录的是任务状态、工具调用事实与证据，不要求保存模型内部推理过程。

### F-09 Codex 修复与 Pi 回归

通过调用返回值将结果交给 Codex。Codex 依据问题和证据修改业务代码后，提交包含原 `run_id`／`finding_id` 的回归任务，由 Pi 在新快照上执行原复现测试及相关回归。

回归报告应说明原问题是否仍存在、是否出现其他失败以及测试是否发生变化。若预期行为经用户确认发生变更，应显式记录依据，不能静默调整原断言。系统不得形成 Pi 再调用 Codex、Codex 再递归调用 Pi 的失控循环。

## 6. CLI 与 MCP 接口要求

### 6.1 自研 CLI

下列 `test-agent` 只是命令占位符，最终 CLI 名称待定，不能据此将工具 `askJEV` 改名。

```bash
test-agent doctor --config ./agent-config.json
test-agent run --request ./task.json --format json
```

`doctor` 用于检查必需配置、后端连接与执行环境；不得默认打印密钥或运行有副作用的项目命令。`run` 默认同步等待任务完成、超时或取消，再返回结果。调用预算必须有限，并与 Codex 侧工具超时协调。

机器模式下 stdout 只能包含协议约定的最终 JSON；进度和诊断写 stderr 或事件文件，不能混入启动横幅和模型自由文本。人类模式可以展示可读摘要，但两种模式共享同一结果对象。

建议退出码：`0`＝任务完成且无已确认缺陷；`1`＝任务完成且存在已确认缺陷；`2`＝输入／配置无效；`3`＝运行失败或受阻；`4`＝仅部分完成；`5`＝已取消。出现部分完成且已有缺陷时，以 `4` 表示不完整，缺陷仍保存在结果内。退出码是本项目约定，不等同于测试框架自己的退出码。

同步执行收到取消信号或父调用结束时，应按策略停止 Pi 和测试子进程、保存已有结果；不得静默留下运行中的故障注入或测试进程。若后续引入异步任务，必须同时提供任务查询与取消能力，不能只返回一个不可追踪的 ID。

### 6.2 MCP 适配器

选用 MCP 时，至少提供一次性执行工具 `run_test_task`，接收同一 `TestTask` 并返回同一 `RunResult`。工具名称为本稿建议。对执行时间超过调用窗口的任务，另行采用成套的 `start_test_task`、`get_test_task`、`cancel_test_task`，而不是承诺无限等待。

Codex 官方 MCP 文档列出本地 STDIO 与 Streamable HTTP 等服务接入方式；本项目具体选择由运行环境决定，不必同时实现全部传输。[T5]

MCP 协议封装与 CLI 文本输出必须分开；STDIO 的 stdout 专用于协议消息。远程部署必须做身份验证、项目授权和路径映射，不能允许调用者读取服务器任意 `repo_path`。远端产物返回调用方可访问的授权引用，或受限的内联内容，不能只返回服务器本地路径。

### 6.3 Codex 检测 Skill

Skill 必须说明何时检测、如何从任务获取项目与范围、调用选定入口、如何等待或查询、怎样识别部分结果及基础设施失败，以及修复后如何发起回归。CLI／MCP 不可用时明确报告原因，不得假装完成检测，也不能用 Codex 自己写测试来静默替代该能力。

## 7. 数据模型与数据流约定

所有对象带 `schema_version`；运行级关联使用 `run_id`，版本使用 `snapshot_id`，检查项使用 `case_id`，测试使用 `test_id`，缺陷使用 `finding_id`。必需字段缺失时拒绝或标记错误，不靠模型猜补。以下为本项目拟定内部协议，不是对 Jive 现有 API 的断言。

### 7.1 核心对象

| 对象 | 关键字段与要求 |
| --- | --- |
| TestTask | schema_version、request_id、目标、项目定位、范围、需求引用、预算、策略配置、可选回归关联。远程项目由授权 project_id 映射。 |
| InspectionItem | case_id、目标文件／符号、前提与场景、预期行为、预期来源、未知项。未确认的预期标注 hypothesis。 |
| PreparedContext | run_id、snapshot_id、需求摘要与引用、相关源码原文和位置／摘要、依赖片段、检查项集合、上下文摘要值与截断标记。由 Pi 整理。 |
| ScoringResult | 对应 ID、逐项状态、score_kind、命题、分值及范围、方向、比较集合、模型／后端版本、原始结果引用和错误。 |
| TestExecution | test_id、关联 case_id、快照、测试文件、命令、环境、结果、断言与日志引用、时间和可用覆盖数据。 |
| Finding | finding_id、关联 case_id／test_id、快照、分类、标题、位置、预期与实际、复现步骤、证据、严重性及依据、复现限制。 |
| RunResult | run_status、assessment、统计、缺陷集合、未完成项、警告／错误、报告与证据引用、版本清单、回归关联。 |

### 7.2 任务请求示例

示例名称、预算与 ID 仅展示字段，不是已确定的项目配置。

```json
{
  "schema_version": "0.1",
  "request_id": "demo-request-001",
  "project": {"repo_path": "/workspace/example"},
  "objective": "检查任务重试是否会造成重复创建",
  "scope": {"include": ["src/jobs/**", "tests/jobs/**"]},
  "requirement_refs": ["specs/jobs.md#idempotency"],
  "budget": {
    "max_duration_seconds": 600,
    "max_cases": 20,
    "max_iterations": 3
  },
  "policy_profile": "isolated-test",
  "scoring_profile": "jive-confirmed-contract",
  "output_format": "json"
}
```

### 7.3 评分返回示例

以下 `0.18` 为演示值。该结构是适配层的统一返回，只有后端语义确认后才允许使用相应 `score_kind` 和方向。

```json
{
  "schema_version": "0.1",
  "run_id": "demo-run-001",
  "snapshot_id": "demo-snapshot-001",
  "backend_mode": "real",
  "backend_version": "demo-version",
  "items": [{
    "case_id": "retry-001",
    "status": "scored",
    "proposition": "相同 task_id 重试后最终只有一条记录",
    "score_kind": "satisfaction_support",
    "score": 0.18,
    "score_range": [0, 1],
    "priority_direction": "lower_first",
    "comparison_group": "idempotency-v1",
    "calibrated_on_project": false
  }]
}
```

逐项状态建议为 `scored`、`needs_context`、`unscored`、`invalid`、`error`。非 `scored` 状态的 `score` 必须为 `null` 或缺省，不得以零分表示失败。分数类型未知或方向冲突时不得进入自动排序。

源码引用必须能在当前数据链路中解析；远程 Jive 无法读取本机路径时，由适配器传递批准的源码内容或授权可解析引用，而不是仅传本地文件名。任何原始数据和证据引用都受同样的权限与脱敏规则约束。

### 7.4 最终结果字段

`run_status` 表示执行是否完整，建议值为 `completed`、`partial`、`blocked`、`failed`、`cancelled`。`assessment` 独立表示发现情况，建议值为 `confirmed_findings`、`no_confirmed_findings`、`inconclusive`；“部分完成但已发现缺陷”可以同时成立。

统计至少包括计划项、已评分项、已执行测试、通过、失败、跳过、基线失败、新确认缺陷和未完成项。报告与产物至少包括 `result.json`、`report.md`、测试文件／补丁、执行证据和 `manifest.json`。文件名可配置，但返回对象中必须有稳定引用与内容类型。

### 7.5 状态推进与失败规则

主流程为 `received → preparing → scoring → planning → generating → executing → analyzing → reporting → completed`。实现可以合并内部状态，但对外必须可区分准备、评分、测试和报告阶段；预算内允许从分析阶段回到规划或补充信息。

评分不可用时按配置选择阻塞或降级，报告必须注明未使用 Jive 排序。预算耗尽返回部分结果；取消保存已有证据。最终报告写入失败不得以普通成功结束；至少保留可恢复的结构化错误或任务记录。

## 8. 权限、隔离与非功能要求

### 8.1 执行与数据安全

源码、需求、日志和 Jive 返回内容均作为任务数据处理，不得因其中出现指令而覆盖系统策略。仅加载团队批准的 Skills／扩展；仓库中可执行配置和测试命令也需受信任策略控制。

Pi 只能写批准的测试文件、夹具、报告与缓存目录；业务源码修改交给 Codex。限制必须覆盖 shell、脚本、符号链接和测试子进程，不能只限制编辑工具。按目标环境选择容器、虚拟机或具备实际读写限制的执行器；单纯工作副本不等于安全沙箱。

默认不向执行环境提供生产凭据。Jive 和生成模型凭据由受控连接层使用，不写入 Skill、任务文件或模型上下文；不把宿主环境变量全部继承给测试进程。网络访问、依赖安装和故障注入按策略授权。默认禁止生产故障注入、擅自清理项目、破坏性 Git 操作和自动提交业务修改。

上下文采用最小必要范围，排除密钥、无关个人数据及其他禁止外发文件。日志和报告脱敏；对调试原始内容的留存需要单独配置权限和保留期限。不能将“会做脱敏”视为允许默认上传全部仓库。

### 8.2 稳定性与可追溯

每项模型请求和测试执行都有有限超时；任务有总预算与迭代上限。取消后清理子进程及临时故障状态，保留必要证据。测试执行的重试只能在明确安全或隔离重置后进行，不能按评分重试逻辑盲目重跑有副作用操作。

运行清单记录快照、Pi 改造版本、工具／Skill 版本、模型与评分配置版本、测试框架和环境信息。生成式过程不要求跨运行完全相同，但生成后的测试、输入与命令应足以复现报告中的结果。

机器输出采用稳定 Schema，字段变更遵循版本管理。任何超时、未执行、降级和无法确认的结论都显式呈现，不能以“无 bug”掩盖。

### 8.3 性能与效果衡量

首版记录准备、评分、生成、执行与报告耗时，以及调用次数和可取得的用量，不预设没有实测依据的吞吐或缺陷提升比例。运行时必须暴露预算配置，并在预算到达时停止新增工作。

“发现更多 bug”属于效果目标而非未经验证的能力保证。后续评估应在相同项目、候选集合与总预算下比较 Pi 不带评分和 Pi 加 `askJEV` 的已确认去重缺陷数、首次发现耗时及误报；将评分成本计入预算。该评估与基本功能验收分开。

## 9. 配置与部署要求

配置分为生成模型、Jive 后端、执行环境、测试策略、输出存储五部分。模型标识、服务地址、凭据引用、超时、重试、上下文限制、任务预算、允许路径和网络策略不得写死在 Skill 中；秘密值不写入普通配置样例。

生成模型和 Jive 后端必须能够独立配置与部署。Pi／CLI 的运行位置与测试执行位置可相同，也可分离；本地路径与远程项目映射须明确。现有两台 DGX Spark 分别承载评分与生成服务的构想可作为目标部署方案，但具体硬件、模型、驱动与部署方式尚未冻结，不作为本稿已经验证的兼容性结论。

开发团队首先清点现有 `askJEV` 实现与 Pi 改造点，复用可用代码；本文没有指定重做工具、替换后端或从零训练模型。交付需要声明最低运行环境、已支持测试框架及安装方式，并在目标环境完成一次真实后端联调。

## 10. 验收标准

下列 P0 为首版必须。涉及入口的条目按所选择的 CLI／MCP 路线验收；另一入口列入后续范围时再验收，不构成同时建设的隐含要求。

| 编号 | 等级 | 验收场景与通过条件 |
| --- | --- | --- |
| AC-01 | P0 | 从选定入口提交任务后，实际经过改造后的 Pi、askJEV、Jive、测试执行和报告链路，能关联同一 run_id。 |
| AC-02 | P0 | 对受控样例检查输入：上下文由 Pi 整理，包含必要源码与预期依据；askJEV 不额外生成业务分析。 |
| AC-03 | P0 | Skill 与工具分别交付并可定位版本；缺少 askJEV 工具或后端配置时明确失败，不假装只凭 Skill 完成评分。 |
| AC-04 | P0 | 在声明正确性支持分数的固定样例中，低分项获得优先补测，指定基础测试仍执行；方向未定义时不猜测排序。 |
| AC-05 | P0 | 用 Mock 注入超时、鉴权失败、非法分数、未知／重复 case_id，均得到相应错误，不被映射成有效低分。 |
| AC-06 | P0 | 真实 Jive 后端完成至少一轮请求与结果关联验证；Mock 结果有显著标记，不能混入真实验收记录。 |
| AC-07 | P0 | Pi 为含已知缺陷的受控项目生成并执行测试；失败报告含预期来源、实际断言、命令、快照和可复现证据。 |
| AC-08 | P0 | 环境故障、测试语法错误和基线失败可区分，不被报告成新确认产品缺陷。 |
| AC-09 | P0 | 执行前后业务文件按策略比对无擅自修改；测试写入限定目录，用户原工作区修改不丢失。 |
| AC-10 | P0 | Codex 的检测 Skill 能消费结果；Codex 修复后再次调用 Pi，回归报告关联原缺陷且不静默削弱断言。 |
| AC-11 | P0 | CLI 机器模式 stdout 可直接解析，退出码与结构化状态一致；若选择 MCP，协议消息和返回 Schema 合法。 |
| AC-12 | P0 | 超时、取消和预算耗尽后停止新增执行，清理子进程／故障状态，并返回可用的部分结果或明确错误。 |
| AC-13 | P0 | 任务中的未提交代码被纳入快照；代码更新后生成新快照，旧评分不冒充新版本结果。 |
| AC-14 | P0 | 结果含范围、执行统计、未完成项、问题证据和版本；全通过时不出现“已证明无 bug”等结论。 |
| AC-15 | P0 | 凭据不出现在 Skill、模型输入和普通日志中；越权路径、未批准网络与故障注入请求被阻止。 |
| AC-16 | P1 | 第二入口实现后，同一任务的字段语义与核心流程一致；长任务查询与取消能完整工作。 |

效果评估另交实验报告，不以几个成功示例替代总体结论，也不将没有达到未约定的提升幅度视为基础接口未完成。
