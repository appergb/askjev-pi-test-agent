# 1.1 真实 GitHub 仓库测试与项目完成度

日期：2026-09-21。

## 结论

测试智能体已经能够对一个真实的小型 JavaScript 仓库生成并执行有效测试，将有证据的 bug 通过 CLI 交给 coding agent，并验证修复后的原测试回归。本次由 Pi 生成业务测试，Codex 消费交接包、审查断言并修改独立源码副本，反馈协议记录了缺陷不再复现。

当前定位是**真实小项目可用的工程试用版**。尚不能称为通用、无人值守的自动测试平台。尤其是评分后端的优先级效果尚未通过验证，可靠结论来自实际执行的断言。

## 仓库和测试方法

选择 [lukeed/klona](https://github.com/lukeed/klona)，MIT 许可。固定提交为 `e563341d88f433e74a9b4c3c0372d4ba55d2f79e`，包版本 2.0.6。它具备明确的深拷贝契约和多种数据类型，源码精简，适合验证当前工具的真实适用范围。

原仓库位于本机 `artifacts/github/klona`，源码保持干净，未植入缺陷。`artifacts/github/klona-fixed` 是修复副本。没有向上游提交 issue、PR 或代码。

先运行原有 uvu 测试；再由 Pi 阅读 README 和原始 .js 源码，整理检查项、调用云端 Open JEV、生成 node:test 测试并在沙箱执行。原有测试通过 jiti 兼容其无扩展名导入，测试正文和业务源码都没有被改写。

初轮是普通类型与常见行为测试。初轮通过后，由调用方明确发起合法非默认构造参数、边界和内部状态的专项任务。后续 full 模式任务另行覆盖属性描述符与 Symbol。这里不能宣称模型在完全无人干预的一次通用请求中自动覆盖了所有边界。

## 找到的 bug

DataView 的 byteOffset 和 byteLength 在克隆时丢失。例如在 8 字节缓冲区上创建 `new DataView(buffer, 4, 4)`，返回的克隆却覆盖整个 8 字节缓冲区，长度和可见字节都发生变化。full 模式的独立视图和混合对象测试也复现了相同问题。

原因在[默认实现第 67 行](https://github.com/lukeed/klona/blob/e563341d88f433e74a9b4c3c0372d4ba55d2f79e/src/index.js#L67)和[full 实现第 32 行](https://github.com/lukeed/klona/blob/e563341d88f433e74a9b4c3c0372d4ba55d2f79e/src/full.js#L32)：构造新视图时只传入克隆后的 buffer，没有传递原视图的偏移和长度。

Codex 消费 Pi 的交接文件后，在两个分支的构造调用中补上传递 `x.byteOffset` 和 `x.byteLength`。修复补丁保存在 [dataview-fix.patch](../../examples/github-klona/dataview-fix.patch)，原 Pi 测试没有被改写或放宽。

## bug 如何反馈给 coding agent

运行完成后，CLI 返回 result.json 和 coding-handoff.json 的路径。调用方执行 `handoff --from <run>`，获得确认缺陷、源文件、Git 提交与工作区修改状态、需求原文、Pi 测试路径及摘要、失败日志和回归参数。

本轮 Codex 实际读取该交接包，核对测试和源码后修复独立副本。`regress` 在新快照执行原测试，`feedback` 校验原运行关联、测试摘要和基线结果，写入 coding-feedback.json。记录的状态是 `regression_passed`，对应失败检查项是 `not_reproduced_after_fix`。

这是可被 coding agent 直接调用和消费的结构化接口；尚未实现自动向任意 coding agent 会话推送任务，也没有 MCP 服务端。

## 本次完善的内容与实际暴露的问题

1. 原来只接受 .mjs，现在能直接测试上游原始 .js/.cjs，不通过改名源码来迁就 demo。
2. 新增上游测试基线，原测试失败会先阻断发现阶段，不会被算作新 bug；原测试文件也参与快照摘要。
3. 新增 Git 提交、原文件是否修改的来源记录，以及 coding-handoff/feedback 协议。
4. 首次真实请求因整份 README 使评分输入超过 4096 tokens 而失败。现改为发送引用源码和对应需求摘录；生成模型仍能阅读所选完整上下文。
5. 初次 full 模式尝试曾因引用字符串校验反复失败而缩水为 1 个简单测试。该历史结果不作为 full 模式通过证据。新增稳定需求 ID 和 min_cases 后，重新生成并执行了 8 组测试，发现两个失败记录。
6. 不再给每个确认问题机械赋予 medium 严重性，实际业务影响留给调用方评估；报告保留证据事实。

## 后续优先级

优先扩大真实仓库与明确契约的评估集，验证一次通用任务的漏测率；其次改进评分模型或评分协议，并在同一预算下比较有/无评分的结果；再扩展依赖管理、其他测试框架和跨平台执行。MCP 可以复用现有交接契约，但不应先于这些可靠性工作。
