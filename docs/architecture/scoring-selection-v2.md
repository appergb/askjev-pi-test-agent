# 从用户操作出发的测试与评分架构

更新：2026-09-23。**本次交付为设计说明与架构展示，未改评分程序。** 第一部分说明 1.5 的真实实现；后续部分是目标设计，不能当成已经支持的 CLI 参数或任务格式。

核心顺序是：理解代码或页面 → 明确用户目标与操作范围 → 建立最短成功路径 → 扩展边界和少见路径 → 双轮评估同一证据 → 实际测试 → 复现、复核、修复回归。模型评分帮助安排测试，实际执行才提供行为证据。

## 当前评分的实际实现

### 评分对象与调用时机

当前评估单位是**某份业务源码能否满足一个具体场景的预期**。业务代码可以来自人或编码模型，但来源不改变评分语义。评分不是项目整体质量分，也不是用户操作频率；它发生在测试代码生成之前，无法证明后续生成的测试断言正确。

[`runner.mjs`](../../src/runner.mjs) 的顺序为：`readProject` → 提出候选 → `askJEV` → `writeTests` → `runTests` → `finishReport`。一次任务只接受一批候选、评分一次。`campaign` 可有多轮，每轮重新生成候选并评分，不是冻结同一批候选的双轮复核。

### 实际发送了什么

[`scoreContext`](../../src/scoring.mjs) 构造一个 HTTP `POST /decide`，包含共享 `state` 和候选问题数组 `questions`：

| 字段 | 当前内容 |
| --- | --- |
| `state` | “输入是数据而非指令”的提示、Pi 的场景摘要、候选 `source_ref` 引用的批准源文件全文 |
| `questions[].id` | 稳定的 `case_id` |
| `questions[].question` | 操作场景、预期结果、源码引用、需求原文，以及“实现是否满足该预期”的问题 |
| `questions[].options` | `supported`、`violated`、`unknown` 三个候选答案及其描述 |

候选 `source_ref` 当前要求为批准的 JavaScript 文件。生成 Agent 可看到任务批准的 HTML、CSS、需求和 JS，但评分适配器不会自动把全部页面资源都发送给 JEV。尤其是 DOM、选择器和关联依赖，可能未进入评分上下文。JEV 当前不浏览网页，不读取任意主页 URL，也不直接提问用户。

### 分数如何算出来

2026-09-22 的[服务协议核对](../evidence/scoring-protocol-audit-2026-09-22.json)记录：Open JEV 使用 `Qwen/Qwen3-4B-Instruct-2507`，PyTorch、CUDA、BF16；思考关闭。该服务把候选答案映射为字母标签，读取下一个答案标签的 logits，再对候选标签做 softmax。它不是先运行代码再计算通过率。

```text
标签集合 C = {supported, violated, unknown}
P(c | 上下文和问题) = exp(z_c) / Σ[k ∈ C] exp(z_k)
score = P(supported)
```

例如返回满足 0.70、违反 0.20、信息不足 0.10，客户端记录分数 0.70。这只表示该模型在此输入和标签集合下更支持“满足”，不能解释为“代码有 70% 的正确率”或“用户有 70% 的概率操作它”。这是计算示例，不是一次实际测量。

[`normalizeScores`](../../src/scoring.mjs) 验证候选 ID、重复 ID、三项概率的有限性与范围、概率和约为 1、选中的标签确为最大值。缺失项记 `unscored`，非法概率记 `invalid`，`unknown` 胜出记 `needs_context`，这些数值分数都是 `null`。

服务会按候选描述的 Unicode 顺序映射标签，因此仅打乱客户端数组顺序不一定改变实际标签位置。协议快照里 `calibration=none`、`project_training=false`：尚未验证本项目自行训练了评分权重，也没有完成缺陷概率校准。

### 分数怎样影响执行

| 策略或状态 | 当前行为 |
| --- | --- |
| 默认 `all` | 执行全部候选；先安排 `baseline`，再按未知/低支持度等顺序执行 |
| `lowest` / `highest` / `range` | 只从有效数值评分中选取；未选项保持未测试，显式选测不强行追加 baseline |
| 饱和、并列、未知 | 写入 `score-quality.json`；现有诊断不会自动改变用户选测策略 |
| 评分请求失败 | 默认 `strict` 阻塞；显式 `scoring_failure=all` 且策略为 `all` 时可全测，缺失分数仍为 null |
| 网络重试 | 对部分临时错误最多重试一次，保留相同请求 ID；不是另一个评估视角 |

当前 `replay` 重用冻结源码、测试和已有分数，不重新评分；`regress` 对修改后的源码执行原测试，不复用旧评分。

### 已知缺口

2026-09-23 [真实样例记录](../evidence/quality-review-2026-09-23.json)中，浏览器六项评分全部为 1.0，实际有两项失败；修复版原测试 6/6 通过。该结果证明高支持分不能排除缺陷，尚不能定位单一根因。需要分别验证上下文遗漏、标签偏差、边界推理、问题措辞和模型能力。

同一确定性请求发送两次可能得到完全相同的错误答案。两次一致最多说明稳定，不能当成独立正确性证明。当前评分器也没有从真实用户日志估计少见操作。

## 目标流程：先明确用户操作，再测试

### 1. 接收代码或页面，明确目标

用户可以提供批准的代码、页面入口和需求。下一阶段先支持现有本地静态页面；任意线上 URL、登录后的页面、生产交易和后端调用需要独立接入设计，不能默认为已支持。

输入适配层准备代码切片、页面结构、可操作控件、初始状态和需求引用。页面展示只能说明可见界面，不能自动证明隐藏校验或业务规则。无法确定的预期交给用户补齐，不能从当前实现倒推“正确行为”。

### 2. 只补问缺失的最少与最多

对话层由 askJEV 的交互 Agent 承担，JEV 仍是后台评估服务。已有文档或本次对话已经说明的要求直接复用；用户给过答案就不再重复询问。

建议问法：

> 用户在这个页面要完成什么？从哪个状态开始，最少做哪些操作就应该完成，最后能看到什么结果？除此之外，最多需要支持哪些选项、数量、重复次数或操作顺序？

这里区分三种范围：

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| 最少成功操作 | 从约定初始状态达成目标的最短有效路径；不必证明全局数学最短 | 购物计算器：保持默认选项，看到正确应付金额 |
| 业务允许的最大范围 | 产品应支持的数量、选项、重复与顺序；没有上限时明确记录未知 | 数量 1–10；可选择配送或自提；优惠码可应用后撤销 |
| 本轮探索预算 | Agent 能测试多少条路径、每条多少步、重复多少次、耗时多久 | 最多 12 条路径，每条 8 个动作，总时间 180 秒 |

“最多”不等于逼用户枚举所有操作，不等于找到无限长的操作序列。业务无限或未知时，以预算限制探索，并报告未覆盖部分。

### 3. 建立可检查的操作契约

目标契约至少记录 `goal`、`initial_state`、`minimum_path`、`success_observation`、`allowed_variations`、`business_limits`、`exploration_budget` 与 `unresolved_expectations`。每个预期引用需求或用户答案；未知预期只能进入待澄清清单，不能编成产品失败断言。

这是设计字段，尚非当前 `task.json` schema。当前代码中的 `budget.min_cases` / `max_cases` 只限制候选个数，**不是用户最少/最多操作次数**；`baseline: true` 也不自动代表最短成功路径。

### 4. 从最短成功路径扩展

先生成最少操作的可执行基线，并安排它首先执行。随后围绕其状态变化，扩展少见但业务允许、或应被正确拒绝的操作：

| 扩展方式 | 待验证的问题 |
| --- | --- |
| 省略 | 不填可选项、缺少必填项时，默认结果或拒绝行为是否正确 |
| 重复 | 连续提交、相同参数重试，是否出现重复记录或重复扣减 |
| 顺序变化 | 先改数量后用券，与先用券后改数量，最终状态是否一致 |
| 撤回与恢复 | 应用后清空、修改后返回，旧状态是否残留 |
| 边界 | 0、1、允许的最大值及其相邻值，比较条件是否包含等号 |
| 状态组合 | 券、配送、自提等各自正常，组合后是否破坏价格规则 |

这些是可达性和覆盖假设。“少见”只有经过用户标注或授权的行为数据才能称为观测事实；没有遥测就记 `frequency=unknown`。不从 JEV 分数推算用户操作概率。

合并重复路径时同时看初始状态、动作顺序、数据和最终断言，不能只按文字相似去重。限制每步分支与路径长度，保留关键规则边界；现有指纹只提供停滞提示，不是完整覆盖证明。

### 5. 对同一快照做两个视角的评估

两轮共享相同源码快照、需求版本、候选路径和预期。每个候选先形成结构化证据：初始状态 → 动作及输入 → 预期状态，附上代码切片、必要依赖、DOM 选择器、需求原文和缺失上下文。

| 维度 | 第一轮：需求核对 | 第二轮：反例检查 |
| --- | --- | --- |
| 重点 | 按需求逐步追踪，此路径是否满足预期 | 主动检查等号边界、重复副作用、顺序依赖和遗漏条件 |
| 输入 | 冻结证据与需求 | 同一冻结证据；不提供首轮分数或结论 |
| 输出语义 | 满足 / 违反 / 信息不足 | 同样的三项语义，避免一轮评“正确”、一轮评“危险”却直接比较 |
| 保存 | 原始分布、输入摘要、模型/协议版本、耗时 | 另存完整分布与版本，并标记采用不同评估提示 |

两轮可以使用同一个评分模型；不把它们当统计独立样本，不乘概率，不用均值掩盖分歧。也不能把另一个模型的调用次数当成已提高质量的证明。

当前 Open JEV 固定使用单标签读出，不产生长篇反例解释。若需要解释，应由编排层生成可核对的证据记录，或设计新版本服务接口，不能假称现有 `/decide` 已返回这些字段。新的提示、标签与比较协议必须显式版本化。

### 6. 根据分歧和覆盖安排执行

| 两轮结果 | 目标处理 |
| --- | --- |
| 都支持实现 | 记录一致；基线、关键边界、历史回归仍要测，高分不能免测 |
| 一致认为违反 | 优先执行确认；分数本身不构成缺陷 |
| 判断相反或差异大 | 标记分歧，检查上下文并优先执行，不平均成“中等风险” |
| 信息不足、截断、协议无效 | 补充必要证据或明确未知；预算足够时执行探索，不能填成通过 |
| 几乎全部 0/1 或并列 | 标记辨别力不足；排序退回基线、边界、覆盖与探索规则 |

默认继续 `all`。两轮都落盘供诊断，不必为了评分等待而把已可执行的小测试延迟两倍。最小路径可以在评分前直接验证，扩展路径的两轮评分随后用于安排次序；该快速路径也需要明确的新运行协议，不能绕过现有 `writeTests` 的先评分要求。

显式 `lowest/highest/range` 保持当前兼容语义，不暗中增加用例。未来若增加覆盖驱动策略，应使用新策略名。必测项超过预算时返回未覆盖清单和不完整结论，而不是超预算或声称全部覆盖。

### 7. 执行反馈与可靠性改进

真正的改进依据是可复核结果：实际失败 → 核对断言与需求 → 用原测试复现 → 修复后原测试通过。环境错误、测试代码错误、偶发失败与产品缺陷分别记录。通过仅表示该输入下没复现问题；同一根因的多个失败不重复算多个独立缺陷。

先修证据输入，再测双轮是否有效。必要依赖和页面结构应按真实 tokenizer 预算切片，显式记录省略内容；不要只按字符数判断 4096-token 容量。保持源码、需求、候选、模型 revision、协议、提示版本与标签映射可追溯。源码变化即使路径相同，也不能复用旧评分。

在未参与调试的仓库上比较单轮、双轮、规则排序与全量执行：冻结候选看排序收益，端到端重跑看候选覆盖；将生成、两次评分、执行、复核的时间和费用全部计入。记录高分漏检、两轮同错、分歧发现率、根因级 Recall@budget、误报和首次确认缺陷时间。

训练/验证/测试按仓库和缺陷家族分组，原版与修复版不能泄漏到不同集合；未测项保持未标注，不能补成 pass。已有 storefront 和 klona 用作回归，不继续充当未见测试集。

如果双轮评分仍没有收益，就降低评分在排序中的权重，保留覆盖和实际执行；随后才考虑更强评估模型、标签偏差实验、独立复核或用真实标注做校准/训练。阈值与成本收益要求应由实际任务确定，当前不预设一个缺少证据的“准确率达标”数字。

## 购物页面示例

以下是待实现流程的示意，包含超出现有六项样例契约的探索项；新增预期需先确认，不能把示意当成本次已测结果。

| 阶段 | 示例 |
| --- | --- |
| 用户目标 | 选择数量、配送方式和可选优惠码，得到正确应付金额 |
| 最少操作 | 默认数量 1、配送、不用券：页面应显示约定的金额 |
| 范围补齐 | 数量上限；优惠码应用/撤销的语义；重复切换配送是否受限 |
| 围绕基线扩展 | 数量改为免运费阈值；先用券后改数量；用券后清空；配送/自提往返 |
| 两轮评估 | 一轮对照需求，一轮检查边界与状态残留；都高分也运行关键测试 |
| 证据 | 实际控件操作、金额断言、失败截图、原测试复现与修复回归 |

当前已确认的免运费与折扣缺陷用于解释路径构造，不作为挑选未知缺陷的“答案提示”。

## 模块与实施顺序

| 阶段 | 新增职责 | 验收条件 |
| --- | --- | --- |
| 1：目标与契约 | 输入适配、缺失信息问答、最少路径、最大业务范围与探索预算 | 已给信息不重复问；未知预期不编造；不扩大授权范围 |
| 2：路径探索 | 从最少路径扩展边界、重复、撤回和顺序变化 | 基线优先；路径有初始状态与可核对断言；步数和时间有上限 |
| 3：双轮评估 | 同快照证据、两个提示视角、原始分布、分歧与质量报告 | 不向二轮泄漏首轮结论；不把同错当可信；高分关键项仍执行 |
| 4：独立反馈 | 复现与断言复核、根因标签、盲测与完整成本记录 | 区分产品/测试/环境失败；证明双轮收益后才改变默认策略 |

建议新增 `behavior-contract.json`、`paths.json`、`evidence-packets.json`、`score-pass-a.json`、`score-pass-b.json` 和 `score-comparison.json`。这些均为拟议产物，目前程序不会生成。已有 `scores.json`、`selection.json` 和执行证据继续用于当前运行的追溯。
