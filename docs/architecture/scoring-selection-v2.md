# askJEV Agent 评分与选测架构设计

状态：目标设计，2026-09-22。1.5 已实现评分饱和/并列/未知项诊断、可选 all 故障降级与有预算的多轮测试/失败重现，见 [持续测试](../campaigns.md)。本文完整质量门、hybrid 调度、独立复核、标注与校准仍未实现；SVG 展示目标架构。

![目标架构](scoring-selection-v2.svg)

## 1. 结论与目标

目前有用的是自动生成测试、真实执行、复现证据和修复回归。尚未证实的是“按原始分数筛选，能在节约整体成本的同时保持缺陷检出能力”。改进目标应为**在给定总时间与费用下，发现更多经过复核的独立缺陷，并明确剩余覆盖缺口**。

短期保持 `all` 为默认；`lowest/highest/range` 保留为用户显式选择的实验策略。下一阶段引入 `hybrid`，把需求覆盖与必测规则放在模型分数之前。没有可靠信号时扩大测试或返回覆盖不足，不能把“高分”当作免测凭证。

本次样例只有六项，浏览器执行累计约 3.90 秒，完整低分三项流程约 21.10 秒。重放耗时不包含候选生成、评分和分析，不能据此声称整体加速四倍。对执行成本很低的小任务，新增多次评分可能比直接全测更贵。

## 2. 故障证据与根因分层

| 证据 | 已确认的问题 | 不能直接推断的内容 |
| --- | --- | --- |
| 1.3 免运费边界失败，supported=1.0 | 高支持分不能排除缺陷 | 不能据此断定所有分数都无用 |
| 1.3 五个候选同为 1.0 | 排序信息不足；按 case_id 打破并列不体现风险 | 不能把并列后的先后当风险差异 |
| 1.4 最低分一项未检出，随后全量发现两个预置缺陷 | 当前选测存在漏检；生成候选/表述变化影响结果 | 这两轮候选并未冻结，不能当作严格排序消融实验 |
| 评分服务实时 report：single next-token label softmax，calibration=none | 测得的是答案标签的相对支持度，未校准为缺陷概率 | 不是用户操作频率，也不是软件正确率 |
| 当前输入是候选摘要、引用源文件和需求摘录 | 缺少稳定的结构化证据与覆盖特征 | 标签位置偏差、提示词影响、缺失依赖需分别消融验证 |
| 当前数值筛选排除 unknown/无效值 | 未知项可能永远得不到测试 | 不能将 unknown 静默转成零分 |

`src/scoring.mjs` 已经校验 ID、概率范围和分布；当前未发现“分数方向写反”的证据。主要问题是**评分语义、辨别能力和选测策略之间没有可靠保障**，不是简单把升序改成降序。

## 3. 优化顺序

### A. 先修选测机制，控制漏检

1. **小任务优先全测**：依据历史执行时间估计，当全部候选在总预算内且没有昂贵副作用时，直接全测；冷启动没有成本数据的小候选集先跑全量建立基线。评分可在影子模式记录，不影响选择。
2. **必测集合**：由需求、改动和已有回归清单建立，不由生成模型的 baseline 布尔值独自决定。至少覆盖改动命中的既有缺陷回归、关键业务规则及其边界；规则只扩展候选，不自动宣称存在 bug。
3. **混合选测**：必测之后，剩余容量初始按约 50% 风险、30% 覆盖增益、20% 探索分配；这是待验证的起始配置，不是最优参数。小预算用确定的配额取整规则，容量足够时至少保留一个探索名额。
4. **探索包含高分与未知项**：按业务分支/场景簇分层抽样，记录随机种子、抽样概率与未选原因。先去重再补满配额；不同槽位不能重复计入预算。
5. **预算冲突显式呈现**：必测集超过预算时不暗中增加执行量。按业务影响和覆盖选出可执行部分，返回 `budget_insufficient` / `inconclusive` 和未覆盖的必测项。如果用户明确要求只测一项，严格执行一项并告知无法保证覆盖两个独立缺陷。

### B. 再修评分输入与质量判断

每个候选生成一个固定字段的 evidence packet：`case_id`、需求原文及摘要、源文件/函数/依赖摘要、具体输入、预期输出、关联分支、边界类别、上下文是否完整、快照摘要。生成时把“需求期望”和“实现行为”分开，不能用实现反推期望。

采用针对该候选的最小代码切片，包含必要依赖与 HTML 选择器。按评分服务的实际 tokenizer 预算切片，给协议和答案标签预留容量；不能只按字符长度估算 4096-token 限制。记录被省略的依赖，缺失关键依据时请求补充或标记需探索。

边界场景结构化，例如：数量 5 → 小计 100；需求为小计 ≥100 免运费；实现条件为小计 >100。可以增加受限 AST/算术检查作为独立特征，禁止用任意 eval 执行业务代码。如此形成的风险特征不能代替浏览器真实断言。

质量门检查：

- 协议合法性：ID、revision、快照、概率、缺失项，保留现有检查。
- 饱和/并列：候选分数几乎全相同、有效不同分数过少；将模型权重设为零或降级，而不是靠 case_id 选“最危险”项。
- 上下文完整性：关键依赖遗漏、截断、不同候选证据尺度不一致。
- 稳定性：对代表项进行语义保持的改写与标签映射置换；持续变化才增加评估，避免每项固定调用多个模型。
- 分歧：确定性边界规则与评分矛盾、不同评估器判断不一致时，提高探索优先级，不取平均掩盖分歧。
- 版本与漂移：模型、协议、模板或候选来源变化后使旧校准器失效，回到影子评估。

实时协议对候选描述按 Unicode 排序。**只打乱客户端 options 顺序可能没有改变实际答案标签**；检验位置/标签偏差时必须在可控后端实验中改变映射，并升级 protocol 版本。

低熵不代表可信：错误的 1.0 同样具有低熵。温度校准也不能纠正模型对边界语义的误判。先验证输入、标签读出和判别能力，再讨论概率校准。

### C. 最后建立可学习的排序器

在校准数据不足时只输出 `risk_hint`、不确定性和规则依据，不输出 `failure_probability`。初始排序分可以是：

```text
priority(i | S) = [w_r·risk_hint(i)
                   + w_c·coverage_gain(i | S)
                   + w_u·uncertainty(i)
                   + w_h·historical_regression_risk(i)] / estimated_cost(i)
```

各特征归一化，成本设置合理下界，避免极小估计值支配排序；必测约束先于这个分数。`coverage_gain` 在每次选入后更新，以防同一行为被多个相似场景占满。业务影响作为约束或单独权重；有真实用户行为遥测时，访问频率可以加入影响分析，绝不从模型 token 概率推导。

有足够的独立标注之后，比较逻辑回归、轻量排序模型与规则基线；评估温度/Platt/保序校准，按验证集选择，不预先宣布某种算法有效。若使用已校准的 `p(defect | evidence)`，质量门必须确认校准器适用于当前任务分布，且不能与覆盖/探索保障混为一谈。

## 4. 模块与数据流

| 模块 | 输入与输出 | 实现位置/状态 |
| --- | --- | --- |
| Task & Snapshot | 授权范围、预算、需求 → 不可变快照 | 现有 common / runner，继续复用 |
| Candidate & Evidence | 需求与快照 → 场景、结构化证据、稳定 candidate hash | 新增 evidence-builder / coverage-model |
| Scoring Adapter | evidence → 原始标签 logits/概率、质量信息与版本 | 扩展现有 scoring；保留 raw 分数语义 |
| Quality Gate | 协议/完整性/饱和/分歧 → model signal enabled/degraded | 新增 score-quality |
| Selection Planner | 必测集合、特征、预算 → 有原因的选测与跳过记录 | 扩展 selection；新增 hybrid，旧模式不变 |
| Execution & Verification | 选中计划 → Node/Chrome 实测、复现、缺陷复核 | 复用执行器；新增独立断言复核与重现预算 |
| Feedback & Evaluation | 有证据的结果 → 根因标签、成本、校准/排序训练样本 | 扩展 handoff / feedback；新增 evaluation store |
| Session & Scheduler | 会话、资源预算 → 有限并发和取消 | 复用会话管理；全局并发/费用限制待增 |

候选缓存键必须包含快照、需求、证据、模型 revision、protocol/template 和候选映射；有学习模型时再包含 calibrator/ranker 版本。源码、需求或模板变化后不得复用旧分数。CUDA 前缀缓存只是推理加速，不能当成评分结果缓存。

建议新增工件：`evidence-packets.json`、`score-quality.json`、`coverage.json`、`selection-v2.json`、`labels.jsonl`。保留现有 scores.json 与 selection.json 用于兼容；新协议显式使用新版本。

示意契约（尚非 1.4 CLI 输入）：

```json
{
  "schema_version": "2.0",
  "mode": "hybrid",
  "budget": {"wall_ms": 30000, "max_cases": 6},
  "model_signal": {"quality": "degraded", "reason": "score_saturation"},
  "selected": [
    {"case_id": "shipping-boundary", "reasons": ["mandatory_boundary"]},
    {"case_id": "coupon-discount", "reasons": ["risk_hint", "new_rule_coverage"]}
  ],
  "skipped": [],
  "coverage_complete": false,
  "uncovered_obligations": ["remaining obligations must be computed, not inferred"]
}
```

## 5. 本次两个 bug 在新策略中如何处理

- **免运费**：需求中存在 ≥100 的边界，生成低于、等于和高于边界的候选；边界检查成为必测义务。supported=1.0 不能把它移除。
- **优惠码**：百分比规则和总价恒等式各有覆盖义务，折扣场景与普通无券场景不归为同一簇。0.00247 可以影响优先级，但不作为确认缺陷的证据。
- 预算足够时执行全部六项，复核两个根因；预算为两项时，优先覆盖这两个独立规则是本样例的设计目标，必须通过冻结候选的测试验证，不能事后用 bug 答案构造一个“完美策略”。
- 预算只有一项时，无论选哪一项，都无法保证发现两个独立缺陷。应明确显示未覆盖规则，而不是声称已经解决漏检。

## 6. 数据、评估与上线门槛

**建立真值**：断言失败先标记候选问题；独立复核需求与断言，重复复现并验证修复后原测试通过，才给 confirmed-defect 标签。测试错误、环境故障、偶发失败分开。通过只表示该输入未复现失败，不是整个功能正确。按根因去重，避免多个断言重复计为收益。

**防止选择偏差**：训练数据不能只有低分已测项。周期性执行完整候选集，其他任务保留分层随机探索，记录 selection propensity。学习时可采用适当的加权或分层校正，并报告估计方差；未测试数据保持 unlabeled，不补成 pass。

**两层实验**：

1. 冻结源码、需求、候选、测试和分数，比较 all、随机、原 lowest、覆盖规则、hybrid。多随机种子报告不确定性。这里的 recall 是“全量候选实测可发现的已知独立缺陷”上的相对召回，不是全软件召回。
2. 端到端重复生成并执行，测候选稳定性和整个系统的检出能力；统计实际生成/评分/复核/浏览器时间、费用和修复交接误报，不能用冻结重放代替。

训练/验证/测试按仓库和缺陷家族划分；同一缺陷的原版、修复版、变体不得跨集合泄漏。既有 storefront / klona 只作开发回归，新增未参与调参的仓库与历史缺陷、正确版本、修复版本作保留评估。变异测试仅补充，单独报告等价变异和非真实缺陷。

主要指标：根因级 Recall@budget、首次确认缺陷时间、确认缺陷数/总费用、交接误报率、必测规则覆盖率、高分审计漏检率、排名对措辞的稳定性。概率模型额外报告 Brier score、分层可靠性图与 ECE，不能仅用“15 次里 12 次正确”判断可用。

建议上线门槛（待按业务容忍度确认，不是已达成的指标）：在保留集上，以仓库为单位估计区间，hybrid 相对全量可检出缺陷召回率的单侧 95% 下限 ≥95%，同时总成本下降 ≥20%；关键回归集不允许新增漏检。达不到则维持 all 默认。少量样本不支持高置信度，应继续影子运行。

## 7. 阶段与验收

| 阶段 | 交付 | 验收条件 |
| --- | --- | --- |
| P0 可观测性 | 原始标签/上下文覆盖/饱和报告、总成本账本 | 复现 1.0 高分误判；能说明每个未测原因；小预算不越界 |
| P1 策略保障 | 需求边界候选、必测覆盖、hybrid、未知与高分探索、后端降级 | 冻结测试验证选择集合；服务失败仍可按覆盖策略运行并显式标记降级；严格实验模式保持原语义 |
| P2 评估与校准 | 多仓库真值、分层抽样、排序/校准器、影子对照 | 达到约定的统计门槛后才考虑改变默认策略 |
| P3 增强 | 根据失败追加邻近边界/组合场景、独立复核、成本自适应、模型蒸馏/训练 | 在同总预算下证明新增能力带来的独立缺陷收益；训练需独立数据与GPU预算 |

训练不是第一步。先修覆盖、输入和反馈闭环，再评估是否需要更强评分模型、LoRA/监督微调或蒸馏；现有项目未执行这些训练。

## 8. DGX Spark 接入原则

已部署的 GPU 评分和生成服务继续复用，详见 [NVIDIA 技术清单](nvidia-stack.md)。评分质量优化与 GPU 性能优化分开验收。采用有限队列、小批量、模板前缀复用与取消传播；只有量测确定瓶颈后才调整并发、量化或 CUDA 路径。

模型服务可支持 262K 上下文，不表示当前 CLI 的 16 KB 输入约束已取消；评分服务仍有 4096-token 上限。共享 GPU 的新增评估/复核调用可能影响交互延迟，应预留评分通道并记录排队时间。
